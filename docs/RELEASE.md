# GitHub Releases

1. Configure and test the existing Namecheap API. Complete the physical-device, mail and multi-device tests in TESTING.md. Resolve remaining limitations and publish an accurate privacy notice naming the actual service operator.
2. Run `npm ci`, unit checks, PHP lint and browser tests. Build/sync the web assets and create a signed release APK using BUILD.md. Use a higher versionCode for each release. Verify its signing certificate and SHA-256.
3. Review source and packaging before making the repository public. Include `src`, `android`, `backend` source/schema, lockfile, tests, scripts and docs. `.gitignore` excludes `.tools`, node_modules, built APKs, local.properties, private production config, uploads and signing materials. Inspect Git's actual staged changes; an ignore file cannot remove an already-tracked secret.
4. Original application code includes an MIT license in `LICENSE`. Review that choice before public distribution. No license grant for third-party religious content is implied by a code license. Preserve `docs/CONTENT-LICENSE.txt` and dependency licenses. Bundled translations are provided under Tanzil's noncommercial terms; keep the product free of commercial use unless permission is obtained.
5. The optional `.github/workflows/android.yml` builds a **debug** artifact on pushed source. It has no signing secrets and does not publish a release. Public distribution should normally use the separately signed release APK.
6. Create the public repository and push only reviewed source. Create a version tag matching the Android version. In GitHub → Releases → Draft a new release, select the tag and attach the signed APK, checksums, source archive if desired and concise release notes listing supported Android versions and known restrictions.
7. Installation instructions: download APK on the phone, verify the published checksum/signature where practical, allow installation from the selected browser/file manager, install, launch, confirm location/time zone and grant notifications/alarms if wanted. Existing installations must use the same signing key for upgrades.

Do not attach keystores, passwords, config/production.php, exported personal data, upload directories or entire local build-tool folders to a release. Do not call a debug or unsigned artifact a production signed APK. No GitHub repository or release has been published automatically by this task.
