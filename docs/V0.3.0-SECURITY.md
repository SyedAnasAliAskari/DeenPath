# DeenPath 0.3.0 security and provider review

The package ID, account identities, API v1, database names and hosting paths are preserved. PHP uses its explicit expanded table allowlist, owner-scoped prepared queries, version checks, per-operation UUID deduplication and the existing per-account transaction lock. New tables inherit the owner key and cascading account deletion. Private-record validation permits only the encrypted payload/format, rejecting accidental plaintext fields. Existing HTTPS-only network policy, private file ownership/quota checks, token rotation and idempotent sync remain in place.

Protection, reflections, journal and optionally synchronized chat history are serialized into AES-256-GCM ciphertext **before** entering the SQLite snapshot, operation queue or PHP database. Each operation uses a new random 96-bit IV and authenticated tag. The random private master key is held in an Android Keystore-encrypted, account-scoped vault. This is field encryption, not whole-database encryption: ordinary prayer/routine data, record identities, update times and limited reminder metadata remain visible to the local app/backend. Ciphertext tampering and wrong-key failures are tested; actual Android Keystore behavior needs device verification.

The optional PIN is a separate privacy gate, not the encryption password. PIN verification uses a random salt and PBKDF2-HMAC-SHA256 with 210,000 iterations; the verification configuration is itself inside the Keystore-backed vault. Failed PIN attempts wait 30 seconds. Native biometric success unlocks the same short-lived gate. It is not a biometric CryptoObject binding to every decrypt operation. The UI relocks on backgrounding, section exit and configured inactivity; native authorization expires after at most ten minutes. FLAG_SECURE protects private-section screenshots/recent-app previews where Android honors it. No claim is made against a rooted/compromised device or malicious code running inside the authorized app process.

Encryption keys do not synchronize automatically. A user-exported recovery backup wraps the master key with a 12+ character password, PBKDF2-HMAC-SHA256 and AES-GCM, alongside ciphertext records. Uninstall normally removes the device key; recovery requires that backup/password. Restoring a different key can make current ciphertext unreadable, so the UI explicitly asks for a backup first. A forgotten PIN can be bypassed only through enrolled device biometrics; no insecure reset silently decrypts data. The browser preview deliberately keeps private entries in memory, with no plaintext persistence or provider credentials.

User-owned Gemini credentials are kept in account-scoped Keystore-backed vaults, excluded from snapshots, operation queues, source archives, app-provided configuration and logs. The only destination is a fixed `https://generativelanguage.googleapis.com/v1beta/models/{validated-model}:generateContent` REST endpoint, with `x-goog-api-key` authentication, redirects disabled and finite connection/read timeouts. Context is bounded to recent messages; no app records, profile, journal or habit reflections are automatically added. Model and key input is validated. HTTP failures return status codes without echoing provider response bodies that could include confidential request information.

Provider order is personal billed Gemini, then personal Gemini free-tier if configured and explicitly allowed; at most one request per connection is attempted per send, with a ten-second native request interval per account/connection. There is no app-owned shared key and no server AI proxy. Model-generated text is treated as unverified. Matching references may display the actual bundled source separately; this does not certify the explanation or any alleged quotation. Local lessons share the existing attributed Tanzil corpus.

Official documentation consulted: [Gemini REST](https://ai.google.dev/api/generate-content), [API setup](https://ai.google.dev/gemini-api/docs/quickstart), [OAuth prerequisites](https://ai.google.dev/gemini-api/docs/oauth), [terms](https://ai.google.dev/gemini-api/terms), [Android biometric authentication](https://developer.android.com/identity/sign-in/biometric-auth), [GeomagneticField](https://developer.android.com/reference/android/hardware/GeomagneticField), [SensorManager](https://developer.android.com/reference/android/hardware/SensorManager). Current terms restrict developer/professional use, age and regions; unpaid data may improve services and be reviewed by humans. A general consumer launch requires a fresh provider/terms review. Google Sign-In does not itself provision personal Gemini API quota. Rasikh documentation at `https://api.rasikh.ai/docs` could not be retrieved; authentication, quota, conversational capability and licensing remain unverified and no calls are made.

This is a local code/privacy review, not a penetration-test certificate. Physical biometric/PIN flows, screenshot restrictions, recovery across two real devices, live provider HTTP responses, shared-host SQL isolation and email still need integration testing with authorized accounts and hardware.
